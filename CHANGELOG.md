# Changelog

## v0.16.0 (28.09.2026)

Продукт целиком ориентирован на русский регион, а установка и обновление
приведены к одному пути. Релиз собран из проверенных на стенде изменений.

### Решения
- **Интерфейс русскоязычный.** Поддержка en отменена, вместе с ней и инфраструктура, которая выглядела её следом, но ничего не делала.
- **Один нативный установщик.** Поддерживается `bash deploy/setup.sh -m native`; отдельный `deploy/native/install.sh` удалён.

### Убрано
- `apps/web/src/lib/i18n.ts` — 14 ключей, из которых использовался один; убраны импорты `useI18n` в `AppNav` и `settings/page.tsx`, подписи меню заданы прямо в компонентах. `useFormatters` реэкспортировался из этого файла — импорты перенаправлены в `@/lib/dates`.
- Варианты формата даты `auto` и `en`: `auto` молча превращался в `ru`, а время и числа всегда форматировались в `ru-RU`, поэтому оба варианта в настройках вводили в заблуждение. Остались `ДД.ММ.ГГГГ` и `ГГГГ-ММ-ДД` для выгрузок. Сохранённые значения `auto`/`en` автоматически приводятся к `ru` при загрузке настроек.
- `deploy/native/install.sh` — параллельный нативный установщик: из 12 возможностей умел 2 (распаковка релиза и права). Не ставил Node.js, PostgreSQL и nginx, не генерировал сертификаты, не проверял подключение к БД, не умел секреты в файлах и health-проверку. Ни в одной инструкции не упоминался, но попадал в комплект. Обновление нативной установки по-прежнему отдельным шагом: `deploy/native/upgrade.sh`.

### Добавлено
- `scripts/bump-version.mjs` и `npm run version:bump` / `version:check`: версия меняется одной командой во всех 7 местах и в `package-lock.json`, а согласованность проверяется в CI. Раньше версия жила в 11 файлах, и забытое место уже дважды давало расхождение на стенде.

### План развития
- Пункт о локализации переписан и закрыт: язык — русский, форматы дат `ru`/`iso`, время и числа в `ru-RU`, часовой пояс пользователя, валюта ₽, переключатель языка не планируется. В планах остался один пункт — современный стиль интерфейса.

## v0.15.2 (28.09.2026)

Приёмка на чистой установке и обновлении. Все три исправления — из реальных прогонов, а не из кода.

### Исправлено
- **План развития в портале не обновлялся.** Данные хранились в двух копиях: `roadmapData.json` (страница и генератор `ROADMAP.md`) и литерал в API, а `/api/portal-roadmap` отдавал вторую. Правки источника не доезжали до пользователей. Теперь `seed.ts` генерируется из JSON (`npm run roadmap`), в CI стоит проверка расхождения (`check-portal-roadmap-sync.mjs`).
- **Обновление применялось к чужому compose-проекту.** В `docker-compose.prod.yml` зашито имя проекта по умолчанию, а установщик спрашивает своё; `update.sh` не передавал `-p`, поэтому пересоздавал контейнеры другого проекта на той же машине вместо своей установки. Имя теперь берётся из `.env`, а для старых установок — из меток работающих контейнеров.
- **Обновление в файловом режиме секретов ломало установку.** `update.sh` не подключал `deploy/docker-compose.secrets.yml`, поэтому пересозданный API оставался без `DATABASE_URL` и `JWT_SECRET`. Установщик теперь пишет в `.env` `COMPOSE_PROJECT_NAME`, `SECRETS_MODE` и `IMAGE_SOURCE`, а для установок, созданных до 0.15.2, режимы выводятся по файлам на диске.

### Добавлено
- `compose.sh` — обёртка над `docker compose`, создаётся установщиком: подставляет имя проекта и override-файлы (файловые секреты, оффлайн-образы). Команды в `install.md`, `updates.md` и в итогах установки переведены на неё: без неё забытый файл compose снимает секреты с API.
- `scripts/check-k8s-manifests.py` и `deploy/k8s/preflight.sh` — статическая проверка манифестов (в CI при каждом пуше) и предпроверка окружения перед первым `kubectl apply`.
- `deploy/setup.sh --render-k8s` — предпросмотр манифестов без установки, без root и без `kubectl`.
- `THEME-DESIGN.md` — проект современного стиля интерфейса (реализация после базового функционала).

### Проверено на Debian 13
- Чистая установка 0.15.1 оффлайн-бандлом, файловые секреты: контейнеры healthy, 4 миграции, 53 таблицы, сиды 1/5/101, рестарт не дублирует, секреты в файлах 600 и только через `*_FILE` в контейнере.

- Первый вход: меню появляется без F5 (исправлено в 0.15.1).

## v0.15.0
Крупный релиз: закрытый продукт от установки до обновлений. Все проверено на Debian 13 (Docker и нативная установка) и на PostgreSQL 17.

### Установка и развёртывание
- **Комплект для внедрения** `scripts/build-client-kit.sh` — установка без исходников: Docker из реестра, оффлайн, Kubernetes, нативно (systemd) и web-машина. Гайд `install.md`, патчноуты и манифест обновлений в комплекте, контрольные суммы.
- **Установщик доводит машину до готовности сам**: ставит Docker Engine + Compose v2, Node.js 20+ и PostgreSQL с ролью и базой `helpdesk`; проверяет вход в БД паролем **до** запуска сервисов; генерирует сертификаты и администратора; задаёт `umask 022` и права на релиз.
- **Режим `-m web`** для раздельной схемы: на web-машине только интерфейс и nginx с TLS, который проксирует `/api` и `/uploads` на API-машину (пересборка web не нужна). Шаблон — `deploy/native/nginx/web.conf.tpl`.
- **Проверка готовности** `deploy/native/check-readiness.sh`: права релиза, доступ пользователя `helpdesk`, вход в БД, юниты и автозапуск, ответы API/Web, sudoers для авто-обновления из UI (печатает готовую строку `visudo`), reverse-proxy с TLS; есть `--json`.
- **Автообновления без Registry**: оффлайн-бандл (`docker save` + `pull_policy: never`), обновление через `scripts/update.sh --offline`, версия фиксируется в `.env` только после health-check, при ошибке — авто-откат.

### Секреты и безопасность
- **Секреты в файлах вместо `.env`**: схема `<ИМЯ>_FILE` (путь важнее значения) для приложения, миграций и сида; `deploy/docker-compose.secrets.yml` монтирует их как `/run/secrets/*`, поэтому в `docker inspect` секретов нет.
- **Ротация** `deploy/rotate-secrets.sh db|jwt|admin|all`: пароль роли БД, ключ JWT и пароль администратора, с бэкапом и перезапуском сервисов.
- **Лицензирование**: подпись Ed25519, реестр поставщика (`license-server/`), состояния и режимы `off|warn|enforce`, **read-only** при отзыве, вкладка «Настройки → Обслуживание → Лицензия».

### Надёжность
- **Сторож БД**: при нескольких неудачных проверках подряд API пишет причину и завершается кодом 1, чтобы supervisor его поднял (иначе процесс оставался «живым», а запросы падали). Кратковременный сбой процесс не убивает.
- **Оповещения об отказах**: без повторов после перезапуска API (сверка с журналом) и с запасными каналами — если внутренние уведомления не прошли, оповещение уходит по EMAIL/TELEGRAM/NTFY/MAX.
- **Резервные копии**: очистка по сроку хранения работает при любом дампе, а не только по расписанию; проверено на внешней БД (дамп по TCP, тест восстановления — 53 таблицы).

### База данных и права
- **Кастомизация БД**: пул (`min`, `statement_timeout`, `keepalive`), схема, SSL (`verify-ca`/`verify-full`, CA/сертификат/ключ файлом или inline-PEM) — 16 переменных задокументированы, значения валидируются, эффективная конфигурация видна в «Системе».
- **Новое право `system.config.view`**: параметры подключения (хост/порт/БД, пул, SSL) видны только админам; раньше их видел любой, кому лично выдали `system.view`. Метрики остались под `system.view`.
- **SQL перенесён в управляемые миграции Prisma**: `migrate diff` не находит расхождений со схемой, корневые `*.sql` убраны в `archive/sql-legacy/`, а CI проверяет соответствие миграций и схемы на каждом пуше.

### Прочее
- В CI добавлены проверка соответствия миграций схеме (сервис postgres) и ручной запуск релизного workflow.
- Новый гайд `updates.md`: активация обновлений на машине (интерфейс, CLI, переменные) и порядок выпуска версии для разработчика.
- Патчноуты публикуются в публичный репозиторий обновлений скриптом `scripts/publish-manifest.sh` — вручную или релизным workflow; скрипт отказывается публиковать версию, чьи ассеты ещё не опубликованы.

## v0.13.3
- TLS-шлюз: поддержка многохостной установки через `TLS_GATEWAY_MODE=local|remote`.
  - `local` (по умолчанию) — поведение как раньше: API пишет сертификаты в `TLS_CERTS_DIR` и перезагружает nginx через docker.sock.
  - `remote` — шлюз на другой машине: API сохраняет бандл `fullchain.pem`/`privkey.pem`/`meta.json` в `TLS_BUNDLE_DIR`, авто-reload не требуется; бандл скачивается через `GET /api/system/tls/bundle`, применение фиксируется `POST /api/system/tls/remote-applied` (отметка `applied`/`appliedAt`); `reset` удаляет бандл.
- Новые эндпоинты TLS (`tls.manage`): `GET /api/system/tls/bundle` (отдаёт текущие PEM — и для локального, и для внешнего шлюза), `POST /api/system/tls/remote-applied`.
- Изменён ответ `GET /api/system/tls`: поля `deploymentMode`, `location`, для remote — `applied`, `appliedAt`, `bundleDir`.
- Web: карточка TLS показывает бейдж «Локальный/Внешний шлюз»; в remote-режиме — кнопки «Сохранить бандл», «Скачать бандл», «Отметить применённым на шлюзе», «Удалить бандл» и индикатор «ожидает применения / применён на шлюзе».
- Конфигурация (`GET /api/system/config`): блок TLS содержит `deploymentMode` и `bundleDir`; `filesPresent` учитывает режим.
- Исправлена hydration-ошибка `<div>` внутри `<p>`: текстам с бейджами (Режим, Авто-reload, Метод дампа) в карточке конфигурации задан `component="div"`.
- `.env.example`: документированы `TLS_GATEWAY_MODE` и `TLS_BUNDLE_DIR`.
- Версия поднята до 0.13.3.
